CI/CD de octopus: cómo y por qué

Qué automatizamos con GitHub Actions, qué se decidió en cada paso y qué todavía no sabemos. Es la segunda parte del curso de Rust.

Los términos con subrayado punteado se explican al tocarlos.

Estado, con honestidad. ci.yml ya corrió en GitHub (20 de noviembre de 2026) y pasó en macOS, Windows y Linux: formato, clippy con los avisos como error y tests. release.yml todavía no corrió, así que nunca se generó un instalador. Y compilar sin errores no es lo mismo que funcionar: nadie abrió la app en Windows ni en Linux. Los escribió Claude para alguien que recién empieza con Rust y con GitHub Actions: leelos con ojo crítico.

1. Qué es y qué problema resuelve

Son dos ideas distintas que suelen nombrarse juntas:

  • CI (): cada vez que alguien cambia el código, un servidor limpio lo compila y lo prueba solo. Responde "¿este cambio rompió algo?" sin depender de la máquina de nadie.
  • CD (): armar los instaladores de forma automática y dejarlos listos para publicar.

El problema concreto de octopus: solo se probó en una Mac. Prometer Windows y Linux sin compilar ahí sería adivinar. Y los instaladores de otros sistemas no se pueden generar desde una Mac de forma práctica. Un servidor de GitHub con cada sistema resuelve las dos cosas a la vez.

Lo nuestro es entrega y no despliegue continuo: el resultado es un y una persona decide cuándo publicarlo.

3. Los dos flujos

Flujo A: verificar, en cada push a main/master y en cada PR.

  1. Se revisa el formato con , en un trabajo aparte que dura segundos.
  2. En paralelo, macOS, Windows y Linux compilan y corren (los avisos cuentan como error).
  3. Cada sistema corre los tests.
  4. GitHub marca el commit o el PR con verde o rojo, por sistema.

Flujo B: publicar, al subir una etiqueta como v0.1.0.

  1. Un trabajo comprueba que la etiqueta, Cargo.toml y tauri.conf.json tengan la misma versión. Si no, corta antes de gastar tiempo en compilar.
  2. Cuatro trabajos en paralelo: macOS Apple Silicon, macOS Intel, Windows y Linux.
  3. Cada uno compila la app y genera sus instaladores con tauri-action.
  4. Todos los instaladores se suben a un mismo release en borrador. Vos lo revisás y lo publicás.

4. ci.yml explicado

.github/workflows/ci.yml 
name: CI

on:
  push:
    branches: [main, master]
  pull_request:

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

env:
  CARGO_TERM_COLOR: always

jobs:
  fmt:
    runs-on: ubuntu-22.04
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
        with:
          components: rustfmt
      - run: cargo fmt --check

  check:
    name: check (${{ matrix.os }})
    strategy:
      fail-fast: false # que un sistema roto no tape el resultado de los otros
      matrix:
        os: [ubuntu-22.04, windows-latest, macos-latest]
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4

      - name: Dependencias de Linux
        if: runner.os == 'Linux'
        run: |
          sudo apt-get update
          sudo apt-get install -y libwebkit2gtk-4.1-dev libxdo-dev \
            libayatana-appindicator3-dev librsvg2-dev libssl-dev

      - uses: dtolnay/rust-toolchain@stable
        with:
          components: clippy
      - uses: Swatinem/rust-cache@v2

      - run: cargo clippy --all-targets -- -D warnings
      - run: cargo test
FragmentoQué hacePor qué
on: push / pull_requestCorre en cada push a esas ramas y en cada PR.El push cubre lo que ya está integrado; el PR avisa antes de mezclar. Se listan main y master porque el repo todavía no definió cuál usa.
concurrencySi llega un push nuevo a la misma rama, cancela la corrida anterior.Ahorra minutos y evita mirar resultados de un commit que ya quedó viejo.
Trabajo fmtSolo revisa el formato, en Linux.Es lo más barato y lo más probable de fallar. No hace falta repetirlo en tres sistemas: el formato no cambia con el sistema.
de tres sistemasRepite el mismo trabajo en ubuntu-22.04, windows-latest y macos-latest.Es el motivo de todo el CI: octopus tiene código distinto por sistema (#[cfg]) y solo se probó en uno.
fail-fast: falseSi falla un sistema, los otros siguen.Queremos ver todos los problemas de una vez, no descubrirlos de a uno.
Dependencias de LinuxInstala WebKitGTK, libxdo, appindicator y otras con apt, solo si runner.os == 'Linux'.Tauri y enigo las necesitan para compilar en Linux. En Windows y macOS ya viene todo.
ubuntu-22.04 en vez de ubuntu-latestFija la versión de Ubuntu.Tauri 2 necesita webkit2gtk-4.1, que está en esta versión. Fijarla evita que el CI cambie solo cuando GitHub actualiza "latest". Y compilar en una versión más vieja hace que el resultado ande en más distribuciones.
dtolnay/rust-toolchain@stableInstala Rust estable, más clippy o rustfmt según el trabajo.Es la forma más usada de preparar Rust en Actions. El proyecto usa la edición 2024, que pide Rust reciente.
Guarda las dependencias ya compiladas entre corridas.Tauri tiene muchas dependencias. Sin caché, cada corrida recompila todo desde cero.
cargo clippy --all-targets -- -D warningsCorre clippy sobre el código y los tests, y trata cualquier aviso como error.Un aviso que nadie mira se acumula. Con -D warnings el rojo obliga a decidir. El costo está en la sección 6.
cargo testCorre los tests en cada sistema.Hoy son dos y no dependen del sistema, pero así nacen listos cuando haya tests específicos por sistema.

5. release.yml explicado

.github/workflows/release.yml 
name: Release

# Se dispara al subir una etiqueta de versión, por ejemplo: git tag v0.1.0 && git push --tags
on:
  push:
    tags: ["v*"]

jobs:
  version:
    runs-on: ubuntu-22.04
    steps:
      - uses: actions/checkout@v4
      - name: La etiqueta, Cargo.toml y tauri.conf.json tienen que coincidir
        run: |
          tag="${GITHUB_REF_NAME#v}"
          cargo_v=$(grep -m1 '^version' Cargo.toml | cut -d'"' -f2)
          conf_v=$(grep -m1 '"version"' tauri.conf.json | cut -d'"' -f4)
          echo "etiqueta=$tag  Cargo.toml=$cargo_v  tauri.conf.json=$conf_v"
          [ "$tag" = "$cargo_v" ] && [ "$tag" = "$conf_v" ]

  release:
    needs: version
    permissions:
      contents: write # para crear el release y subir los instaladores
    strategy:
      fail-fast: false
      matrix:
        include:
          - { os: macos-latest, target: aarch64-apple-darwin }
          - { os: macos-latest, target: x86_64-apple-darwin }
          - { os: ubuntu-22.04, target: "" }
          - { os: windows-latest, target: "" }
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4

      - name: Dependencias de Linux
        if: runner.os == 'Linux'
        run: |
          sudo apt-get update
          sudo apt-get install -y libwebkit2gtk-4.1-dev libxdo-dev \
            libayatana-appindicator3-dev librsvg2-dev libssl-dev

      - uses: dtolnay/rust-toolchain@stable
        with:
          targets: ${{ matrix.target }}
      - uses: Swatinem/rust-cache@v2
        with:
          key: ${{ matrix.target }}

      - uses: tauri-apps/tauri-action@v0
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        with:
          # el proyecto no tiene package.json: usamos el CLI de Tauri vía npx (Node ya viene en los runners)
          tauriScript: npx --yes @tauri-apps/cli@2
          args: ${{ matrix.target && format('--target {0}', matrix.target) || '' }}
          tagName: ${{ github.ref_name }}
          releaseName: octopus ${{ github.ref_name }}
          releaseDraft: true # queda como borrador: lo revisás y lo publicás a mano
          releaseBody: |
            Instaladores sin firmar, así que el sistema muestra una advertencia la primera vez.
            - macOS: click derecho sobre la app, Abrir. Después hay que darle permiso de Accesibilidad.
            - Windows: SmartScreen, Más información, Ejecutar de todos modos.
            - Linux: los atajos globales solo funcionan en sesiones X11 (no en Wayland).
FragmentoQué hacePor qué
on: push: tags: ["v*"]Corre cuando se sube una que empieza con v.La etiqueta es la decisión humana de "esta versión sale". Un push común no genera instaladores.
Trabajo versionCompara etiqueta, Cargo.toml y tauri.conf.json.La versión vive en tres lugares y es fácil olvidar uno. Sin esta barrera saldría un instalador llamado 0.1.0 dentro de un release v0.2.0.
${GITHUB_REF_NAME#v}Le saca la v inicial al nombre de la etiqueta.La etiqueta es v0.1.0 pero en los archivos la versión es 0.1.0.
grep … | cut …Extrae la versión del Cargo.toml y del JSON con herramientas básicas de shell.Evita instalar nada para una comparación de tres textos. Funciona porque ambos archivos tienen la versión en una sola línea; si se reformatean, hay que revisarlo.
needs: versionEl release espera a que el chequeo pase.Falla rápido y barato, antes de gastar minutos de compilación.
permissions: contents: writeLe da al trabajo permiso de escritura sobre el repo.Hace falta para crear el release y subir archivos. Se declara en este trabajo y no en todo el archivo: el principio de .
matrix.include con cuatro entradasDefine combinaciones de sistema y destino.En macOS hacen falta dos, porque hay Macs Apple Silicon e Intel y cada uno necesita su binario. Windows y Linux usan el destino por defecto del runner.
targets: en el toolchainInstala el destino de Rust que se va a usar.El runner de macOS es Apple Silicon; para compilar la versión Intel hay que agregar ese destino.
tauri-apps/tauri-actionCompila, genera los instaladores y los sube al release.Es la acción oficial del proyecto: sabe qué formatos genera cada sistema y cómo adjuntarlos. La alternativa es escribir esos pasos a mano.
tauriScript: npx --yes @tauri-apps/cli@2Le dice cómo ejecutar el CLI de Tauri.El proyecto no tiene package.json. Así lo usamos también en la máquina local. No está probado dentro de la acción; la alternativa más lenta es cargo install tauri-cli.
args: ${{ … && … || '' }}Agrega --target X solo cuando la entrada tiene un destino.Una sola línea sirve para las cuatro entradas de la matriz. Un texto vacío cuenta como "falso" en esa expresión.
releaseDraft: trueCrea el release como borrador.Nadie ve los instaladores hasta que los revisás y los publicás. Es la red de seguridad de un proceso que todavía no probamos.
releaseBodyTexto del release con avisos.Los instaladores no están firmados y el sistema lo va a mostrar. Mejor avisar que dejar al usuario desconcertado.

6. Decisiones y por qué

DecisiónAlternativaPor qué esta
GitHub ActionsJenkins, GitLab CI, CircleCIEl código va a estar en GitHub, es gratis para repos públicos y no hay servidor que mantener.
CI y release en archivos separadosUn solo archivoSe disparan por motivos distintos y tienen permisos distintos. El de CI nunca necesita escribir en el repo.
El CI no genera instaladoresEmpaquetar en cada pushEmpaquetar es lento y no aporta información que clippy y los tests no den. Se empaqueta solo al publicar.
clippy -D warningsDejar los avisos como avisosMantiene el código limpio desde el principio. El costo: como usamos Rust stable, una versión nueva de Rust puede traer un aviso nuevo y poner el CI en rojo sin que cambie nada del código. Si molesta, se fija la versión de Rust o se relaja esta regla.
Tres sistemas en el CISolo Linux (el más barato)El código tiene ramas por sistema. Compilar solo en Linux no probaría las de Windows y macOS.
Release en borradorPublicar directoEl flujo no está probado. Un borrador permite descartar una corrida mala sin que nadie la haya visto.
Chequeo de versiónConfiar en acordarseEs un error fácil y caro de cometer, y se detecta con cuatro líneas de shell.
Etiquetas mayores en las acciones (@v4)Fijarlas por Es más simple de leer y se actualiza sola con cambios menores. Es menos seguro: si alguien compromete una acción, recibimos el cambio. Fijar por hash y usar Dependabot es la mejora natural.
Sin firma de códigoCertificados de Apple y WindowsCuestan dinero y trámite, y es un MVP. A cambio hay avisos del sistema al instalar, ya documentados en el release.
Sin --locked en cargocargo test --lockedEs una omisión, no una decisión. Con --locked el CI falla si Cargo.lock no está actualizado; conviene agregarlo.

7. Seguridad

  • Permisos mínimos: solo el trabajo de release puede escribir en el repo, y el CI corre sin ese permiso.
  • Sin secretos propios: solo se usa el GITHUB_TOKEN que GitHub genera para cada corrida y expira solo. Nada que filtrar.
  • Acciones de terceros: dtolnay/rust-toolchain, Swatinem/rust-cache y tauri-apps/tauri-action corren con acceso al código. Son proyectos muy usados, pero hay que tratarlas como dependencias y no solo como configuración.
  • PRs de terceros: en un repo público, los PRs de forks corren con permisos reducidos y sin secretos. Con esta configuración eso es suficiente, porque el CI no usa ninguno.

8. Qué no hace todavía

FaltaConsecuencia
release.yml no corrióNo sabemos si el empaquetado genera instaladores correctos en cada sistema. El tauriScript con npx está sin probar. Es la principal incógnita que queda.
No prueba la app en funcionamientoEl CI compila y corre tests unitarios, pero no abre la ventana ni aprieta un atajo. Eso sigue siendo manual y por sistema.
Los instaladores no están firmadosGatekeeper en macOS y SmartScreen en Windows van a avisar. En macOS, además, cada versión nueva pide de nuevo el permiso de Accesibilidad.
Linux solo en X11Los atajos globales no funcionan en Wayland. El CI no puede detectar eso: compilar no es lo mismo que funcionar.
Sin Dependabot ni cargo auditNadie avisa si una dependencia tiene una vulnerabilidad o una versión nueva.
Sin protección de ramaQue el CI esté en rojo no impide mezclar. Eso se configura en GitHub, no en el archivo.

9. Cómo usarlo

Reproducir el CI en tu máquina

Antes de subir un cambio, corré lo mismo que corre el servidor. Si pasa acá, pasa allá (al menos en tu sistema):

cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test

Sacar una versión

# 1. subir la versión en Cargo.toml y en tauri.conf.json (tienen que coincidir)
# 2. commit y push
git commit -am "Versión 0.1.0"
git push

# 3. crear la etiqueta y subirla: esto dispara release.yml
git tag v0.1.0
git push --tags

# 4. esperar los cuatro trabajos (pestaña Actions) y revisar el borrador en Releases
# 5. publicarlo a mano

Si la corrida sale mal

# borrar la etiqueta local y la remota, corregir, y volver a etiquetar
git tag -d v0.1.0
git push --delete origin v0.1.0

Y descartar el release en borrador desde GitHub. Para la primera prueba conviene una etiqueta como v0.1.0-rc1, pero entonces la versión de Cargo.toml y de tauri.conf.json también tiene que ser 0.1.0-rc1, porque el chequeo exige que coincidan.

10. Si falla

Son hipótesis razonables, no fallos confirmados. El CI ya pasó en los tres sistemas con el código actual, así que las filas de compilación (clippy y enigo) no ocurrieron hoy: quedan como guía para cambios futuros. Lo que sigue sin probarse es release.yml. En la pestaña Actions de GitHub, cada sistema tiene su propio registro.

Síntoma probableDóndeCausa probable
Error de compilación que menciona webkit2gtk o xdoLinuxFalta un paquete en el paso de dependencias.
clippy se queja de un import o variable sin usarWindows o LinuxCódigo que solo se usa en macOS (por #[cfg]) queda sin uso en los otros sistemas. Se corrige con #[cfg] o #[allow] en el lugar justo.
Error de compilación en enigo o en el plugin de atajosWindows o LinuxUna dependencia que necesita una configuración distinta en ese sistema.
El chequeo de versión rojoCualquieraLa etiqueta no coincide con Cargo.toml o tauri.conf.json.
tauri-action no encuentra el CLICualquieraEl tauriScript con npx no se ejecutó como esperábamos. Probar con cargo install tauri-cli.
"Resource not accessible by integration" al crear el releaseCualquieraEl repo restringe el GITHUB_TOKEN; hay que revisar los permisos de Actions en la configuración del repo.
Falla solo un sistemaUno de los tresEs exactamente para lo que está fail-fast: false: arreglar ese sistema sin tocar los otros.

11. Ejercicios

  1. Hacer fallar el CI a propósito. En una rama, rompé el formato de una línea o escribí if x == true y mirá cómo reacciona cada trabajo. Es la mejor forma de entender qué mira cada paso.
  2. Agregar --locked a los comandos de cargo y ver qué pasa si Cargo.lock está desactualizado.
  3. Agregar Dependabot (.github/dependabot.yml) para cargo y github-actions.
  4. Fijar las acciones por hash de commit y dejar que Dependabot las actualice.
  5. Agregar cargo audit o cargo deny como trabajo nuevo del CI.
  6. Proteger la rama main en GitHub para exigir que el CI pase antes de mezclar.
  7. Mover el chequeo de versión a un script (scripts/check-version.sh) para correrlo también en tu máquina antes de etiquetar.

Glosario

Integración continua (CI)

Qué es. Un servidor (en GitHub, GitHub Actions) que compila y prueba el proyecto automáticamente en cada cambio.

Por qué acá. Es la forma práctica de saber si anda en Windows y Linux sin tener esas máquinas, y evita que entren cambios que rompen.

Entrega continua (CD)

Qué es. Armar automáticamente lo que se le entrega a los usuarios (los instaladores) y dejarlo listo para publicar. No es lo mismo que el despliegue continuo, donde además se publica solo.

Por qué acá. Acá un humano publica el borrador. Para una app de escritorio sin firma y con un proceso que todavía no probamos, es lo prudente.

Release en borrador

Qué es. Un release de GitHub que solo ven quienes tienen permiso de escritura hasta que lo publicás. Los archivos ya están subidos.

Por qué acá. Es la red de seguridad: permite revisar o descartar una corrida sin que nadie la haya visto.

rustfmt

Qué es. El formateador oficial de Rust: cargo fmt reescribe el código con un estilo único.

Por qué acá. Evita discusiones de estilo y achica los diffs. En el CI se corre con --check para que falle si alguien no formateó.

clippy

Qué es. Un analizador que detecta código que compila pero es sospechoso, poco idiomático o mejorable (cargo clippy).

Por qué acá. Atrapa errores comunes antes de que lleguen a producción. En el CI se corre con -D warnings para que cualquier aviso haga fallar el build.

Matrix (matriz)

Qué es. Una lista de combinaciones (sistema operativo, destino, versión) sobre las que se repite el mismo trabajo, en paralelo.

Por qué acá. Una sola definición cubre macOS, Windows y Linux, sin copiar y pegar el trabajo tres veces.

Caché de dependencias

Qué es. Guardar entre corridas lo que ya se compiló (dependencias, carpeta target) para no rehacerlo.

Por qué acá. Tauri trae muchas dependencias; sin caché, cada corrida recompila todo. Se invalida sola si cambia Cargo.lock o la versión de Rust.

Etiqueta (tag) de Git

Qué es. Un nombre fijo que apunta a un commit concreto, como v0.1.0.

Por qué acá. Marca exactamente qué código es "la versión". Subirla dispara release.yml, así que publicar es una decisión deliberada.

Permisos mínimos

Qué es. Darle a cada pieza solo el acceso que necesita para su tarea, y nada más.

Por qué acá. Si un paso se compromete (una acción de terceros, un script), el daño queda limitado. Por eso solo el trabajo de release puede escribir en el repo.

Fijar por hash de commit

Qué es. Referenciar una acción por su commit exacto (uses: dueño/acción@a1b2c3…) en vez de por una etiqueta como @v4.

Por qué acá. Las etiquetas pueden moverse: quien controle el repo de la acción podría cambiar lo que ejecuta tu CI. El hash no cambia. El costo es tener que actualizarlo, y Dependabot lo automatiza.

Escrito por Claude para una persona que recién empieza con Rust y con GitHub Actions. Describe el estado del repo al escribirlo: ci.yml verificado en los tres sistemas y release.yml todavía sin ejecutar.
